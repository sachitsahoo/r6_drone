Recon UGV — Implementation Notes

Off-spec decisions and open questions, appended as work lands. Started 2026-09-30.

Phase 1 — repo skeleton, build system, CI

Wrote a real core module instead of a placeholder source fileoff-spec

Phase 1 as specified does not call for any code in firmware/core/, but a CMake static library needs at least one translation unit, and the target cross-compile job has nothing to prove without one.

Rather than a dummy file, I wrote firmware/core/time/timestamp.hpp/.cpp: a wraparound-safe elapsed_us(). It directly serves hard rule 7 (integer wraparound handled explicitly and tested), it gives the test harness seven real assertions instead of EXPECT_EQ(1, 1), and every later loop and the comms watchdog will need it.

Judgment call worth reviewing: the watchdog is an owner-reviewed area. I treated a pure timestamp-arithmetic utility as foundational rather than as watchdog logic — it contains no timeout policy, no state, and no decisions. If you consider that over the line, it should move or wait for a design review.

TARGET collides with a reserved CMake if() operatorhazard

if(TARGET x) is a documented CMake operator that tests whether a CMake target named x exists. Writing if(TARGET STREQUAL "host") is parsed as that operator and silently does the wrong thing — no error, just a wrong branch.

The variable name is fixed by CLAUDE.md's documented commands, so every test in CMakeLists.txt dereferences and quotes it: if("${TARGET}" STREQUAL "host"). There is a comment at the definition site explaining why.

Firmware language subset is applied per-target, not globallyoff-spec

CLAUDE.md says to compile with -fno-exceptions -fno-rtti. Those flags are applied to recon_core on both host and stm32 builds, so host tests exercise the same language subset that ships. They are deliberately not applied to the test executable or to GoogleTest, which is built with exceptions enabled.

Consequence: a test file could use a construct that firmware cannot. The purity guard covers firmware/core/ itself, which is the code that ships, so this is a narrow and visible gap rather than a hole in the firewall.

The purity guard enforces hard rule 2 as well as rule 1scope +

The plan called for a CI guard against vendor headers in firmware/core/ (hard rule 1). tools/check_core_purity.py also rejects new, malloc, std::vector, std::string, std::function, throw, and dynamic_cast (hard rule 2).

Same mechanism, same cost, and rule 2 is the one most likely to be violated by reflex while writing ordinary-looking C++. Comments and string literals are blanked before scanning so doc comments can discuss the banned constructs.

The guard's own tests caught a bug that would have made it uselessbug

The first version blanked all string literals before scanning. That also blanked the quoted header path in #include "stm32g4xx_hal.h" — so the guard silently missed every double-quoted vendor include while still reporting angle-bracket ones. It would have read green on the most likely real violation.

Fixed by skipping literal-blanking on preprocessor lines. The four failing tests were what surfaced it; the guard was fixed rather than the tests relaxed.

This is the argument for testing CI guards like production code: a broken guard is worse than no guard, because it reports success.

RESOLVED — CI now uses the same Arm toolchain as the developer machineclosed

Originally CI installed Ubuntu's gcc-arm-none-eabi, measured as gcc 13.2.1 against 15.3.1 locally — two major versions apart, which under -Werror means CI and local can disagree about identical source. Logged as an accepted risk.

Resolved when the install step's cost became visible in a CI log: apt-get was pulling 574 MB and unpacking 3.1 GB on every push, overwhelmingly multilib newlib variants this build never links against. The STM32 job took minutes while the other two finished in about twenty seconds each.

CI now downloads Arm's own 15.3.rel1 release (153 MB, cached after the first run) from gitlab.arm.com — the same upstream the Homebrew cask uses, whose URL pattern is where the exact path came from. Pinned by SHA-256 (563bebb2…, computed locally from the downloaded artifact) so a swapped or tampered tarball fails the job instead of silently compiling firmware. One change fixed both the version skew and the runtime.

Chose a pinned direct download over a third-party setup action: no unaudited action in the supply chain, and the version is pinned in two places that must be bumped together rather than floating.

Python tests need a virtualenv; CLAUDE.md's bare pytest assumes it is activesetup

System Python 3.13 has no pytest, and installing into a Homebrew-managed framework Python is a bad idea. Created .venv/ (gitignored) with requirements-dev.txt. The documented pytest command works once the venv is activated; otherwise it is .venv/bin/pytest.

pyproject.toml pins testpaths and pythonpath so pytest finds the right tests regardless of where it is invoked from.

Generated protocol bindings are gitignoreddecision

protocol/generated/ is not committed. The schema is the single source of truth, so committing its output invites someone editing the generated file and creating two sources of truth. Consequence: every build and every clone must be able to run the generator, which makes the generator a hard build dependency — accepted deliberately.

Protocol slice — schema, generator, codec

COBS encoder dropped the last byte of any payload ending in 0x00bug

The first version trimmed what looked like a redundant trailing length byte, on the theory that it kept the encoding canonical. It is not redundant: when the input ends with a zero, that final length byte is what encodes the zero. Trimming it silently dropped the last byte of every such payload — including a telemetry frame whose last field happened to be zero.

Six tests caught it at once, clustered on trailing-zero inputs. The encoder now uses the standard encoding from the Cheshire & Baker paper, with a comment at the site saying not to re-optimize it.

COBS decoder accepted a zero byte in a literal positionbug

The zero check covered code-byte positions only, so 03 11 00 decoded happily to 11 00. Encoded data must contain no zero anywhere: the caller found that run between two delimiters, so a zero inside it means the stream was already misframed. Now rejected in both positions.

Corrected a wrong test assertion about resynchronizationjudgment

A fuzz test asserted that a valid frame decodes immediately after arbitrary garbage. It does not, and the decoder was right. Garbage ending without a delimiter leaves the decoder accumulating, so the next frame's bytes join that partial run and its delimiter closes garbage-plus-frame, which correctly fails. The frame after that decodes.

This is inherent to delimiter-based framing. Rather than change the code, I wrote the real guarantee down — after arbitrary garbage, at most one subsequent frame is lost — in FrameDecoder's header comment, and replaced the assertion with two tests that pin it in both the delimited and undelimited cases, in both languages.

Worth reviewing: CLAUDE.md says never weaken a test to make it pass. I judged this a wrong assertion rather than a weakened one — the new tests are stricter and name the property. If you disagree, the conversation to have is whether the decoder should promise zero loss, which would mean buffering speculatively.

The schema lint caught a hard-rule-5 violation in my own schemagood sign

First run rejected three parameters named ..._hz: the declared unit is Hz, and unit symbols are case-sensitive, so the suffix must be _Hz to match CLAUDE.md's own voltage_V / current_A examples. Renamed. The check is worth having precisely because that violation looked fine to me.

version_mismatch is counted but not transmitteddeferred

FrameDecoder::Stats tracks seven counters including version_mismatch. The approved LinkStats message carries seven fields, and version_mismatch is not among them — the message set was fixed before the decoder existed.

Adding it is a protocol schema change, which is owner-reviewed, so I did not do it. The counter is observable locally and in tests. Recommendation: add it in a future schema version; a version mismatch is exactly the kind of link problem the operator needs to see, and it costs 4 bytes at 1 Hz.

params.yaml deliberately contains no controller gainsscope

The parameter mechanism needed something to address, but declaring kp/ki/kd would presuppose a PID form — and CLAUDE.md names "PID form" as an example of a choice requiring an ADR. The file holds three telemetry rates and one read-only version readback instead, which exercise the whole get/set/commit path without committing to a controller structure.

Generated code is written into the source tree, not the build treetrade-off

Both the C++ and the Python consumers need one stable path, and pyproject.toml puts protocol/generated on pythonpath. Generating into ${CMAKE_BINARY_DIR} instead would mean two different paths and a second mechanism for the Python side.

Known limitation: two build trees generating concurrently would race on those files. build/ and build-stm32/ are built sequentially here, and CI uses separate jobs on separate checkouts. Revisit if parallel builds ever matter.

PyYAML is now a hard build dependency for the firmwareconsequence

Generated output is gitignored, so every clone and every CI job must run the generator, which imports yaml. A machine with a C++ toolchain but no PyYAML cannot build the firmware.

Accepted deliberately — committing generated code invites editing it, which is the two-sources-of-truth failure the schema exists to prevent. Mitigated by a configure-time check that fails with the exact pip install command and the -DPython3_EXECUTABLE flag, rather than failing mid-build with an ImportError.

Cross-language verification drives a real C++ binarydesign

Generating both languages from one schema guarantees they were built together, not that they behave identically. The frame codec is hand-written in both languages because the frame layout does not vary with the schema, and two implementations can each match ADR 0002 while disagreeing on a block boundary or on which rejection fires first.

So tests/cpp/protocol_vector_tool exposes the real codec on the command line and test_cross_language.py drives it, comparing against protocol/codec.py and against test_vectors.json — whose CRC values come from stdlib zlib and whose COBS values come from the paper, so the vectors are independent of the code they test. The first frame vector is hand-traced byte by byte in that test file.

CRC is computed in software, not by the STM32 CRC peripheraldecision

The G474RE has a hardware CRC unit. Using it would put a vendor dependency inside firmware/core/, which must compile and pass tests on a laptop — the portability firewall the whole architecture rests on.

The software cost is one table lookup and one XOR per byte, constant-time, on about 75 bytes per frame. If profiling ever shows it matters, the correct move is a HAL interface with a peripheral-backed implementation in firmware/stm32/, not an #ifdef in core.

CAD refactor — 70 × 182, direct drive (ADR 0008, ADR 0010)

The chassis became a spine; the IMU moved off the axisoff-spec

The task as stated was "delete the belt train, put the motor on the axis, re-run the sweep". Placing the motor showed that no casing part can reach the axis while a continuous chassis passes every axial station and the casing turns a full relative turn. That contradicts ADR 0005 and R2. The owner approved a spine chassis, a hollow-shaft motor at end A and an IMU ring at r = 4.75 mm in conversation. Recorded as ADR 0010 (Proposed).

The single-pose sweep hid a real collisionbug

In the first design the IMU bridge crossed r = 35 mm at z = 40, where a chassis standoff sat. The sweep never saw it because the standoffs were holes, not rods, and it checked one pose. The sweep now checks parts in different rotation groups over a full turn at 5°, after an exact (r, z) disjointness test proves most pairs clear. A regression test builds the failure case and asserts the sweep catches it.

Belt-era tests replaced, not weakenedjudgment

Eight tests described parts that no longer exist: the drive band ratio, the motor's annular pocket and trim-boss angle, the pulley-offset motor radius, standoff holes, the chassis OD range, disc rotational clearance, and disc boss engagement. Each was replaced with its direct-drive equivalent (shaft through hollow bore, motor in cup, bearing races supported, clearances over a full turn). The inertia window moved from ADR 0006's ~1e-3 to ADR 0008's 0.10–0.20e-3. The owner's 115–125 mm chassis OD range has no counterpart: there is no chassis disc any more.

Axial layout derived instead of hand-placeddesign

The first layout was a list of hand-placed z values that collided with itself four times as parts changed. Every station is now computed in parameters.py from part lengths, so changing the N20's measured length moves everything downstream.

Small fixes found during the rescalebug

The trim boss at 0° and the camera mount shared an angle and an axial station, and were only clear because the boss passed through the lens hole. The bosses moved to z = 55 mm. The camera mount's radius is now solved from its corner, which is what reaches a 65 mm bore first. bought_parts.py referenced a renamed constant; nothing imports it, so no test caught it.

RESOLVED — the tangential term dominates the IMU errorclosed

In chat I said the IMU's offset only matters during tumbles. That only accounted for the centripetal term. The tangential term alpha r at 200 rad/s2 and 4.75 mm is about 5.5°, during hard corrections. It can be removed analytically, since alpha is the derivative of the gyro rate, but that is an estimator change for the owner. Recorded in ADR 0010. With the flat breakout the offset is 3.8 mm and the term about 4.4°.

Staleness pass — 2026-09-30

The ring IMU board was a custom PCB, which is out of scopeoff-spec

The owner asked whether ring boards were odd. They were, and CLAUDE.md excludes custom PCBs. Replaced with an off-the-shelf breakout lying chip-side-down beside the waist. That is also closer to the axis (3.8 mm versus 4.75), because the offset is a stack-up from the rod, not a distance across a board.

Wrong bearing designation, caught by checking a listingbug

I had called a 35 × 44 × 5 bearing a 61807. A 61807 is 35 × 47 × 7; 35 × 44 × 5 is a 6707. Moot now: the larger GM2804H needs a 6708ZZ (40 × 50 × 6), verified against a listing.

Motor changed from a 2208 to a GM2804Hdecision

No 28 mm hollow-shaft gimbal motor with a usable bore could be found. The GM2804H is a stocked part with a 6.5 mm bore. ADR 0011 (Proposed). The cup grew to 37 mm, and every clearance still passes.

Motor flipped: stator on the casing, rotor on the chassisbug

Rewriting R3 exposed that the first refactor bolted the stator, and so the windings, to the chassis. With the power stage in the casing, the three phase leads would have crossed the wire loop — exactly what R3 exists to prevent. Flipped in the CAD. A new test checks that both bolt circles land in material.

Torque budget recomputed; balance trimming is now a requirementfinding

ADR 0008's 22.5 mN m was traced to I·alpha plus a 10 mm sideways CoM offset, with contents guessed at 35% of the shell. With real electronics and the GM2804H's rated point it is 36.4 mN m untrimmed, 106% of rating, with about 2.2 W of heat. Trimmed to 2 mm it is 49–71%. tools/pitch_inertia_budget.py was rewritten for the current machine, and a test now fails if its copied CAD figures drift from the CAD.

Tests changed, with reasonsjudgment

The IMU pad-hole test became a chip-stack-up test. The budget tool's "shell above 75%" assertion became "above 65%": the old figure excluded electronics, and with them the shell is 71%. It was replaced, together with an assertion of ADR 0011's headline finding (untrimmed is at or past rating, trimmed is under 75%). Added: bolt circles in material, and budget-matches-CAD.

Schema text edited, nothing on the wirescope

Two source/comment strings in messages.yaml said "rotates continuously" and "actuator undecided". Text only — no field, ID, type or range changed. The real schema changes (assign 0x03 as a target-angle command; add the wire loop's turn count) are written up as proposals 6 and 7, not applied.

Motor changed again: GM2804H to DM3505, chosen by the ownerdecision

The owner found the Mercury DM3505 (SparkFun ROB-27477): 40 × 16 mm, 8.5 mm bore, 0.09 N m nominal, 12 V, in stock in the US. That is 2.6 times the GM2804H's rated torque. The untrimmed case drops from 106% to 43% of rated, and holding heat from 2.2 W to 0.5 W, so balance trimming went from required back to recommended. The cup grew to 42 mm and the end-A bearing to a 6709ZZ (45 × 55 × 6, verified). The cup floor bore shrank to 10 mm so the rotor's ø15 bolt circle has material; wheel motor A now goes in from the waist end. The cap screws pass within about 1 mm of the bearing groove, so a test guards that. A second option the owner found, the EM3215, was rejected: 6–8 V only, and 31 mN m even at stall.

firmware/hal — interfaces (2026-10-01)

Header layout: firmware/hal/hal/*.hppdecision

Includes read "hal/clock.hpp", matching core's "time/timestamp.hpp" style, with firmware/hal as the include root. That needs the doubled directory name. The alternative, firmware/ as the root, would also expose core/ headers by a second path.

The design rules are enforced by static_assert, not by conventionscope +

compile_check.cpp builds on host and stm32 under the firmware flags and asserts that every interface is abstract with no virtual destructor, that samples are trivially copyable, and that sample fields are float. Checked that the destructor assert actually fires on a violating class. The purity guard was also extended from core to hal, with a test.

Fakes do not clampjudgment

Clamping out-of-range commands is each real implementation's contract. A fake that clamped would hide a core bug that sends a duty of 1.7, so the fakes record exactly what they were given. Fakes also start invalid (samples) and disabled (power stage), so a core test cannot pass without supplying data.

PowerMonitor::latest made ISR-safe, against the first draftoff-spec

The first draft of the header called it "not ISR-safe, I2C". That contradicted the approved rule that latest() returns the last completed reading and never starts a transfer. Corrected to ISR-safe; the I2C happens inside the implementation.

Slice 5 — minimal simulator (2026-10-01)

The placeholder plant is tested open-loop; no loop is closedoff-spec

The todo item said the plant should be "enough to close a loop". Every loop worth closing (velocity PID, FOC, the stabilizer) is owner-reviewed and has no approved design, and the primer forbids writing a control law without one. So the plant is checked against its own analytic first-order solution, and the SIL tests drive a wheel at a fixed duty. Closing the first loop is the first approved controller's job.

SimWheel's output limit saturates; it does not scaleresolved: ADR 0013 Q3

hal::WheelMotor says the implementation "clamps out-of-range values, then applies the per-build output limit". That could mean saturating at ±limit or scaling by limit. The sim saturates: duty 0.1 under a 0.3 limit is applied as 0.1. That reads most naturally as a limit, and it keeps small commands linear. The STM32 implementation must make the same choice, so the owner should confirm it before that implementation is written.

SimWheel implements both WheelMotor and WheelEncoderdesign

They are two views of one shaft, so a single object makes the plant state impossible to desynchronise. core still receives two separate interface references, as it will on the robot. Multiple inheritance of two interfaces with no data needs no RTTI.

Serial link models line rate, buffers and bit errors, and nothing elsedesign

460 800 baud 8N1 with integer credit accounting, so throughput does not depend on step size. An idle line does not bank credit. TX and RX buffers are 256 B placeholders. Errors flip one bit in a byte with a set probability, from a seeded xorshift64 so runs repeat exactly. Not modelled: framing errors, line breaks, Pi-side relay latency or UDP loss.

Every plant constant is a placeholderlimitation

No-load speed 31.4 rad/s, time constants 50/500/50 ms, 1400 counts/rev. The gear ratio is not chosen and nothing has been measured. The values only give the plant a plausible shape. They are named and commented in sim/sim/wheel_plant.hpp and must be replaced by system identification.

Phase 2.1 — wheel velocity loop (ADR 0013, 2026-10-01)

The accepted design overshot; feedforward is now off by defaultamendment

The SIL step test failed at 13% overshoot. My derivation had followed only the feedback path; feedforward adds a closed-loop zero at -14.3 rad/s. The owner chose kff = 0, keeping the parameter. The derivation is in docs/theory/wheel-velocity-loop.md §3.3, and the lesson is recorded in tasks/lessons.md.

No valid speed: feedforward only, integrator frozenoff-spec

The ADR did not say what the controller does on a step with no valid estimate: the first sample, or an encoder plausibility fault. DriveLoop outputs feedforward_only(ref) and does not integrate. With kff = 0 that is zero duty for that one step. Acting on a known-bad measurement was the alternative, and the worse one. The fault flag is exposed for the safety state machine.

Step dt is measured and capped at 10 msoff-spec

kMaxDriveStepDt_s = 0.01. After a stall, integrating the whole gap at once would kick the integrator and jump the ramp. Detecting the stall is LOOP_OVERRUN's job (safety). The first step after construction integrates dt = 0.

Estimator details the ADR left openoff-spec
  • Warm-up: until N+1 samples exist, the estimate spans what is there. It is valid but coarser.
  • Plausibility bound: kMaxPlausibleWheelSpeed_rad_s = 100, about 3x the placeholder no-load speed, plus one count of margin. This is an initial guess; revisit it with the real gear ratio.
  • On a fault the history restarts from the faulting sample, so one glitch does not poison the next 10 ms.
  • Changing the window clears the history, so two window lengths never mix.
Integrator bounded to ±duty_limitoff-spec

This goes beyond conditional integration. If the limit is lowered while ARMED, a stored integrator above it is clipped at once, since it could never be applied anyway.

Generator now emits param defaults, minima and maxima for C++tooling

protocol::param_defaults, param_min and param_max. Core configs initialise from them, and WheelSpeedEstimator static_asserts its buffer size against param_max::wheel_speed_window_samples, so no default is copied by hand. unit_suffix maps m/s^2 to _m_s2. Protocol version stays 1: adding parameters does not change the wire format, and an unknown ID is already Nacked.

Phase 2.2 — safety state machine (ADR 0014, 2026-10-01)

Pure logic in firmware/core/safety/, tested from a complete state × event table and closed against the sim in SIL. No STM32 glue: that is ADR 0015, proposed. Four points the ADR left open are marked open question. Each has a recommendation and was implemented that way, so the owner can accept as-is or change one line.

Open — SafetyStateRequest asking for ESTOP or FAULTopen question

The ADR covers requests for ARMED and DISARMED only. requested_state can also carry ESTOP or FAULT. Implemented: ESTOP acts as an e-stop (a stop is never refused, whichever message asks), and FAULT is refused with Nack(RANGE_REJECT), because FAULT is entered by detectors only. Alternative: refuse both and make EstopRequest the only way in. Recommended: keep as implemented.

Open — what "the link is fresh" means for interlock 3open question

In DISARMED every valid frame feeds the watchdog, and that includes the arm request itself. Counted naively, the interlock could never fail. Implemented: the request's own frame does not count, so an arm request out of silence is refused (context = 3). Any valid frame in the previous 200 ms satisfies it, and the operator app's 50 Hz Heartbeat always does. On arming, the ARMED watchdog starts from the arm request, so the first DriveCommand has 200 ms to arrive. Recommended: keep.

Open — leaving ESTOP with a fault still activeopen question

The ADR says ESTOP is left "by operator request to DISARMED", and that detectors move ARMED or DISARMED to FAULT. It does not say what happens to a detector event during ESTOP. Implemented: detectors keep latching flags and sending Fault frames in ESTOP (and in FAULT) for visibility, without changing state. The DISARMED request out of ESTOP uses the same clear rule as FAULT: flags whose condition is gone are cleared, and if one is still active the reply is Nack(FAULT_ACTIVE) and the state stays ESTOP. That keeps "DISARMED never holds a flag" true, which the table test asserts on every row. Alternative: ESTOP → FAULT. That would add an edge the ADR doesn't have. Recommended: keep.

Open — the Fault frame sent with Nack(ARM_INTERLOCK)open question

The ADR says to send "a Fault frame naming the first condition that failed in context", but not which fault_code. Implemented: fault_code = NONE (an interlock is not a fault, and nothing is latched) and context = the ADR's condition number: 2 fault latched, 3 link stale, 4 stick not centred (core::ArmInterlock). Condition 1 (not DISARMED) has its own Nack reason, NOT_DISARMED, and no Fault frame. Recommended: keep. The operator app must treat Fault(NONE) as "arm refused", not as a fault.

ADR 0014 arithmetic slip: 500 ms is 25 τcl, not 10correction

500 / 20 = 25. The conclusion (no legitimate transient lasts that long) only gets stronger. Recorded as a dated callout in the accepted ADR, per docs/README.md. The schema source note carries the right figure. Lesson added.

One tick, fixed order: e-stop, detectors, watchdog, requestdesign

Every same-millisecond race resolves in the safe direction: an arm request in the tick a fault appears is refused, a clear with the condition still present is refused, and an e-stop beats an arm. The inputs carry at most one SafetyStateRequest per tick, and the glue holds any extra for the next tick (1 ms). EstopRequest is a separate flag, so it is never queued.

Boundaries: comms trips at ≥ 200 ms, LOOP_OVERRUN at > 5000 µsoff-spec

"No feeding frame for 200 ms" is read as silence ≥ 200 ms, so 199 ms holds and 200 ms trips. That matches the ADR's "a lost link brakes 1.0 s after the last command" exactly. The ADR writes LOOP_OVERRUN as gap > 5000 µs, so exactly 5000 is tolerated. Both boundaries are tested on each side.

LOOP_OVERRUN is measured by the supervisor itselfdesign

It is stepped once per motor-loop iteration, so the gap between its own steps is the loop gap. No timer input is needed, and it stays pure. The first step after boot has no gap.

Every timer is bounded by a latch, for the 71.6 min wrapdesign

link_fresh_ latches false at the timeout and fault_braking_ latches true at the brake delay. The stall timer resets outside ARMED. So no interval ever measured approaches 232 µs, even on a robot left DISARMED for hours. Tested by idling 232 µs + 50 ms, at 4 ms ticks, past one stale heartbeat.

WHEEL_STALL details the ADR left openoff-spec
  • Saturated means |duty| ≥ limit − 1e-4. A limit of 0 never counts as saturated.
  • An invalid speed estimate breaks the condition and restarts the timer. ENCODER_FAULT covers the invalid case.
  • Contexts: WHEEL_STALL and ENCODER_FAULT carry a wheel mask (1 left, 2 right), COMMS_TIMEOUT the silence in µs, LOOP_OVERRUN the gap in µs, and the rest 0.
Pitch enable in FAULT = "COMMS_TIMEOUT is the only flag"design

Q6 implemented literally: any second flag, even one latched later, turns the stage off. A watchdog-reset boot has the stage off.

CheckInMonitor: atomic mask, lock-free asserteddesign

check_in() runs in ISRs, so the mask is a std::atomic<uint32_t> and the code static_asserts is_always_lock_free. A lock-based fallback could deadlock against the main loop. should_feed() lives in a .cpp so the STM32 build compiles it. kIwdgTimeout_ms = 50 lives in core so the sim and the future STM32 driver share one constant.

"Rejected and stale frames don't feed the watchdog" is untestable yetlimitation

The supervisor only ever sees frames the glue has validated, so the property belongs to the glue. The decoder half is already tested (bit errors never yield a frame). Stale-timestamp rejection is not implemented anywhere yet. It is in the ADR 0015 proposal.

Sim additions are test-only fault injectorstooling

WheelPlantParams::encoder_reversed, SimWheel::freeze_encoder(), SimWheel::braking(), SimSerialLink::set_cut() (the transmitter still clocks bytes out; nothing arrives), and SimWatchdog (it records instead of resetting). The SIL test's Robot class is test glue, not a draft of the firmware glue.

WIRE_LOOP_LIMIT = 10 is in the schema with no detectorreserved

Reserved for ADR 0009, so the number cannot be taken by something else. Nothing latches it yet.
